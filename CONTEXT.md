# TokTickIT — Domain Glossary

The shared vocabulary for this project. When the code, the docs, and a
conversation disagree about what a word means, this file wins.

This is a glossary, not a specification. It records *what terms mean*, never how
they are implemented.

Terms marked **(Lab 1)** exist in the code today. The rest are defined here
because the product brief already fixes their meaning, and Labs 2–4 build on
them.

---

## Product

### Ticket

A single IT service request. The parent entity of the whole product. A Ticket
header stores the *current* state of the request: ticket number, requester,
category, related system, summary and description, requested priority, IT
priority, current status, ticket owner, important dates, and resolution summary.

A Ticket has five kinds of child records: **Public Comment**, **Internal Note**,
**Action Taken**, **Attachment**, and **Event Log** entry.

> The product brief §1.2 says "No. of Child entities: 5" but lists only four.
> The fifth is the Event Log, which appears as a tab in the reference UI. That
> same screen also labels Actions Taken as "Service Actions" — the canonical
> term here is **Action Taken**.

### Category **(Lab 1)**

The kind of request a Ticket represents. Reference data managed by an
Administrator, not free text.

Lab 1 seeds exactly four: *Account and Access*, *Hardware*, *Software*,
*Network*.

The brief calls these "request categories", "IT request categories" and
"supported request categories" in different places. They are all the same thing:
a **Category**.

A Category has a **display order** — the position it occupies in a list shown to
a person. Display order is a property of the Category, deliberately separate
from whatever identifier the database assigns it: an identifier records when a
row came into existence, not where it belongs in a list. Reordering the
categories does not change which Category is which.

### Related System

The system or asset a Ticket is about — for example a specific laptop model or
an internal application. Reference data, like Category, and managed by an
Administrator.

Category and Related System are **not** interchangeable: Category says *what
kind of problem*, Related System says *what the problem is about*.

### Public Comment

A message on a Ticket visible to both the Requester and IT Staff. Either side
can add one.

### Internal Note

A message on a Ticket visible only to IT Staff and Administrators. A Requester
can never see or add one. This is the sole difference from a Public Comment.

### Action Taken

A record of work IT performed on a Ticket. Unlike a comment, it can be updated
after it is created.

### Attachment

A file attached to a Ticket. Both Requesters and IT Staff can add attachments.

### Event Log

The audit history of a Ticket — what changed, when, and by whom. Generated by
the system rather than written by a person.

## People

### User

An account that can sign in. Every User has exactly **one** Role.

### Requester

The User who raised a Ticket. Can create tickets, view only their own, set the
Requested Priority, respond to IT Staff, confirm or reject a resolution, and
request reopening.

### IT Staff

A User who works tickets. Can take ownership, set IT Priority, change status,
add internal notes, record actions taken, and resolve or close tickets.

### Administrator

An IT Staff member with additional authority over Users and reference data.
Everything IT Staff can do, plus managing accounts, roles, and Categories and
Related Systems.

Administrator is a **superset** of IT Staff, not a separate track.

### Ticket Owner

The IT Staff member currently responsible for a Ticket. A Ticket has at most one
Owner, and the Owner can change over the Ticket's life.

Do not say "assignee" — the canonical term is **Ticket Owner**.

## Priority and status

### Requested Priority

How urgent the **Requester** says the Ticket is. Set by the Requester.

### IT Priority

How urgent **IT** judges the Ticket to be. Set by IT Staff. It may differ from
the Requested Priority, and it is the one that drives IT's own queue.

Never collapse these two into a single "priority" — the product deliberately
keeps both, and the reference UI shows them side by side.

### Current Status

Where the Ticket is in its lifecycle. Distinct from the **Kanban status** of a
GitHub Issue, which tracks *our development work*, not a customer's request.

## System health

### System Status **(Lab 1)**

What the user sees after clicking **Check System**: whether the TokTickIT
service as a whole is usable.

It is **Online** only when *both* the API answers its health check *and* the
categories load from the database. If either fails, the System Status is
**Offline** and an error explains which part failed.

System Status is therefore a **user-facing verdict about the whole vertical
slice**, not the result of any single endpoint.

> This is why `GET /api/health` does not touch the database. The brief fixes its
> response to exactly `{"status":"ok","service":"TokTickIT API"}` (§10.1), so
> adding a database probe would change a contract we were given. Instead the
> client combines both calls. The brief's own failure-case mock — DB stopped,
> screen shows Offline (§Part 4) — only makes sense under this reading.

### Health check **(Lab 1)**

The API's statement that the Express process is alive and serving. It says
nothing about the database.

### Vertical slice **(Lab 1)**

A thin feature cutting through every layer — UI, API, ORM, database — built to
prove the layers work together. Lab 1 as a whole is one vertical slice.
